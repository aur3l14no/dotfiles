# 需求评估

以用户提供的现有进展、核心用途、工期和总人力为约束，结合项目证据，给出可交付的范围。评估粒度与项目成熟度相称；早期项目先看主要能力边界和开发模块。

## 分类与处置

按实际能力分类；一条需求包含不同情况时，拆开判断。

| 类型 | 处置 |
| --- | --- |
| 已经做过 | 核实现有能力覆盖的条件和范围，保留合理要求；必要的适配、联调仍计入工期。 |
| 不确定做没做过 | 定向核实代码、测试、演示或负责人说明。未查到不等于没有；暂不能确认时，写明待核实事项及其对交付的影响。 |
| 稍微改改就能支持 | 写清最小改动，在对应条款旁标补做。把接入、验证和多个小项的累计成本算进去。 |
| 很难改、需要重新开发 | 按大模块归纳，评估必要性、复用或替代方案及工作量。核心需求保留最小可交付范围；非必要且超出预算的建议删减或延期。 |
| 完全不合理 | 指出具体矛盾、不可成立的条件或无法验收的承诺，提出删除或可验证的替代表述。成本高、我们暂时不会做，本身不属于这一类。 |

已有或缺失都不直接决定取舍。结合必要性、实现代价和需求可协商程度给出明确建议；已经确认的取舍落实到相应条款，待定事项说明正文是否已改。

## 交付

- 保留原有结构和合理表述，只改有依据的问题。小改动就地标注，大模块汇总并关联条款；明确区分已实现、待开发、已改文案和待决定。
- 排期区分日历工期与总人力，包含适配、测试、打磨和部署。估算对应明确范围，说明未核实项与待定范围的影响，不因使用 Agent 自动压缩工期。
- 正文、汇总表和估算保持一致。读者应能看清保留、补做、新做、不做及待定的范围。
- 最终评估说明使用 `no-ai-slop` 做文字验收。

在飞书上呈现评估时，读 [飞书 Tips](references/feishu.md)，具体操作使用 `lark-cli` skill。需要取舍示例时，读 [案例](references/cases.md)。

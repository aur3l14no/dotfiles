# 取舍案例

以下来自一次机器人招标需求评估，展示当时条件下的判断。条件变化时重新评估，不把案例结论当作默认规则。

## 安卓 App 与浏览器

- 背景：已有浏览器管理端，原文要求安卓 App；总投入有限，需求允许协商。
- 处置：建议改为浏览器端，复用现有功能；确认后同步修改所有涉及 App 的条款。
- 条件：浏览器能满足实际使用场景。若依赖特定原生能力，应另行评估。

## 语音、RAG 与 Agent

- 背景：已有固定任务编排，完整语音交互和知识库问答尚未实现，但可能属于核心用途。
- 处置：列为新开发模块，优先复用现成框架，将已有任务包装成工具；先估算基础范围，把扩展能力的取舍写清楚。
- 条件：核心用途确实需要这些能力，且为接入、真机联调和打磨预留时间。不能仅因“还没做”就删除。

## 循环、跳过与电量

- 背景：任务执行和管理界面已有，缺少循环、跳过及真机电量接入。
- 处置：在对应条款旁标补做，估算增量工作。整理进正文后，清理获准删除的讨论评论。
- 条件：现有接口与流程足以承接这些改动；表面上小的功能仍可能暴露底层缺口。

## 频率、精度与延迟

- 背景：原文性能承诺与当前配置或实现机制不符，部分指标尚无真机测试依据。
- 处置：区分配置值、实测结果和验收承诺。修正已有依据的不符之处，其余明确待验证条件。
- 条件：当前配置不是能力上限，控制频率也不等于路径更新频率。不能随意换一个数字，或把全部指标改成“以实测为准”。

## 模型框架与运动能力

- 背景：项目支持行为模型接入、replay 和实时 teleop，原文要求任意动作、广泛抗扰动或统一延迟保证。
- 处置：区分框架能力和所选模型的真机能力，将过宽承诺收敛到可验证的模型、动作和使用条件。
- 条件：有模型入口或仿真演示，不能据此确认真机满足所有要求；具体范围仍需结合选定模型及测试判断。
